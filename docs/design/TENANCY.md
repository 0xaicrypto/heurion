# 租户（机构）设计

2026-10-03。目的：患者模块（第二期）上线前，保证不同机构的数据互不可见。决定见 memory：隐私问题用租户隔离解决。

## 1. 概念

| 概念 | 说明 |
|---|---|
| 租户（机构） | 一家医院、一个科室或一个课题组；个人注册的用户自动得到一个「个人租户」 |
| 成员 | 一个用户只属于一个租户（换机构 = 换账号；以后真有跨机构需求再做多租户成员） |
| 角色 | **平台运营**（我们：建 / 停用租户、配额、平台运维，**不看租户的业务数据**）；**机构管理员**（邀请 / 停用成员、机构设置、看本机构审计）；**成员** |

## 2. 数据放在哪里

| 数据 | 归属 | 隔离方式 |
|---|---|---|
| 文档、资料库、数据集、记忆、对话 | 个人（owner） | 维持现状：按 owner 查询、访问前校验归属；owner 只属于一个租户，所以天然不跨租户 |
| **患者、病历、化验、影像、原始报告文件** | **租户** | **每个租户一个独立的 SQLite 数据库文件 + 独立文件目录**：`data/tenants/<tid>/patients.db`、`data/tenants/<tid>/files/` |
| 账号、租户、成员、审计 | 平台 | 主库（现有 platform.db）加 tenant_id |

患者数据用「每租户一个库」而不是在共用表里加 tenant_id：
- 连接本身就限定在一个租户——查询写错了也读不到别的机构（共用表方案里，一个漏写的 `WHERE tenant_id = ?` 就是串号；v1 出过这类事故）；
- 导出、删除、备份可以按机构整体做；删除机构 = 删库文件 + 删密钥；
- 患者模块是新代码，不用改现有的个人数据代码。

## 3. 加密

- 每个租户一把数据密钥（DEK），用平台主密钥（KEK，来自环境变量 / 以后换 KMS）加密后存在主库。
- 患者库里的敏感字段（姓名映射除外——见下）与原始报告文件用 DEK 加密存储；S3 备份是加密后的文件。
- 删除租户时销毁 DEK：即使备份里还有密文也无法恢复（加密擦除）。
- 说明：平台运营方掌握服务器与主密钥，技术上不是「零知识」；靠职责分离、审计与协议约束。需要物理隔离的机构走**独立部署**（同一套代码，单租户）。

## 4. 机构内的访问

- **患者可见范围**：创建者 + 被加入「诊疗组」的成员（最小权限）；可选「本机构全员可见」作为机构设置。
- **机构管理员默认看不到患者内容**（只管成员与设置）；确需查看走「紧急访问」：填写理由、立即生效、记审计并通知患者的创建者。
- **姓名**：患者在系统里用代号（P-0007）；「代号 ↔ 姓名」的对照只存在医生自己的浏览器里，平台不存（与之前的设计一致）。

## 5. 身份与令牌

- 登录令牌、MCP 令牌（aud=mcp）、模型代理令牌都带上租户 id（`t`）。
- 患者相关的 API 与 MCP 工具（patient_list / patient_read / labs_query / patient_record_propose）先用令牌里的 `t` 打开该租户的患者库，再按诊疗组校验——**不存在「传一个别的租户的 id」这种路径**。
- AI 的隔离环境（专属 uid、工作区）维持按用户；患者数据不放进工作区长期保存，分析时按需导出去标识化的副本。

## 6. 模型调用

- 机构设置「患者数据可以发给外部模型」（默认开，对托管版说明清楚）；关闭时患者相关的回合只能用本地模型（以后接入），否则拒绝。
- 发给模型的上下文只用代号，不含姓名。

## 7. 管理界面

- **平台运营页**：租户列表（成员数、存储量、状态）、新建租户并指定首个管理员、停用 / 恢复、配额；平台运维审计。
- **机构管理页**（现「用户管理」改造）：成员与邀请（邀请链接 / 指定邮箱域名自动加入）、角色、停用、机构设置（患者模块开关、外部模型、患者默认可见范围、数据保留期）、本机构审计日志。

## 8. 迁移

- 现有每个用户 → 各自一个个人租户（成员 1 人，本人为机构管理员）。
- 现有平台管理员 → 角色改为「平台运营」，同时是自己个人租户的管理员。
- 个人数据不动（仍按 owner）；患者库从空开始。

## 8.1 双重身份：已有账户加入医院（2026-10-05）

每个账户有两个空间：

| 空间 | 字段 | 用在哪 |
| --- | --- | --- |
| 工作空间 | `users.tenant_id` | 工作台（/app）：患者、临床研究、科室、机构模板、机构审计。加入了医院就是医院，否则是个人空间 |
| 个人空间 | `users.personal_tenant_id` | 知家（/phr）：家人健康档案、分享给医生。加入医院后保留 |

- **迁移**：老库补列，个人租户的用户 `personal_tenant_id = tenant_id`；经邀请注册进机构的纯医院账号为空，第一次用知家时建一个个人空间（`TenantService.personalOf`）。个人租户开始发邀请变成机构时，它只是工作空间，本人的知家另建个人空间。
- **加入**：管理员发邀请链接，或在「机构管理 → 按用户名邀请」填平台上已有账户的用户名（`tenant_invites.target_user_id`，只有这个人能看到 / 接受，也不能拿去注册新账户）。本人在头像菜单「医院邀请」或页面提醒里看确认页（工作台按医院；个人文档仍只属于自己；知家不受影响），**接受**后 `tenant_id` = 医院、`tenant_role` = 邀请角色；可**拒绝**。管理员不能代接受；AI 发起的加入要本人确认（`account.join_tenant`）。同一时间最多加入一家医院（已在别院时邀请发不出、也接受不了）。之后管理员在「机构管理 → 科室」把他分进科室。
- **离开**（本人「退出医院」或管理员「移出」）：`tenant_id` 回到个人空间。取舍：还负责本院研究的必须先转交（或管理员离职交接）才能离开；本院研究成员身份、科室归属去掉；本院患者的诊疗组记录保留（访问日志可追溯），但人离开后读不到（患者库按工作空间取），重新加入后恢复。本院唯一管理员不能退出。
- **空间解析**：`Actor.space`（`tenancy/patients.ts`）→ `TenantService.of(user, space)`。HTTP：`/api/phr/*` 一律个人空间；知家前端对通用患者接口带 `X-Heurion-Space: personal`；其余是工作空间（`http/api.ts` 的 `me()`）。医生一侧的家庭分享（收件箱、查看、纳入）按工作空间。AI：回合所在文档的归属（`docs.context` 里的 `space` / `tenant_id`，知家的健康档案、简报记 `personal`）决定 `aiActor` 的空间（`mcp/server.ts`），AI 不能跨空间读。
- **权限**：医院管理员只看得到本院（工作空间）的患者；成员个人空间的家人档案对任何医院管理员都不存在（404）。

## 9. 测试（上线门槛）

- **跨租户越权测试**：自动枚举所有带 id 的 API 路由与 MCP 工具，用另一个租户的账号带着本租户的 id 调用，必须全部 404 / 拒绝。新加路由不在清单里时测试失败（防止漏测）。
- 机构内：非诊疗组成员、机构管理员（未紧急访问）读患者 → 拒绝；紧急访问留审计。
- 加密：患者库文件、原始报告文件在磁盘上不是明文；销毁 DEK 后不能解密。
- 部署自检加一项：用两个测试租户互相访问。
